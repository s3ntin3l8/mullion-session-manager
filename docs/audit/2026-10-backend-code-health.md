# Code-health audit — backend

**Scope.** Mullion's backend (`src/`, 378 production files), its test tree
(`test/`, 482 files) and the cross-cutting structural findings that reach into
the frontend. The React frontend (`frontend/src/`) is audited separately, in
[2026-10-frontend-code-health.md](2026-10-frontend-code-health.md); the two
reports share one set of cross-cutting findings, so a finding that spans both
is stated once in each with the other side's link.

**Status.** This is a **report-only** pull request. No production code is
refactored here. Every finding is filed as a tracked issue (numbers in the
[Deferred backlog](#deferred-backlog)), and one permanent guardrail lands with
the report: `scripts/check-max-file-lines.mjs`, a ratchet that stops the
largest files from growing further.

Measured against `origin/main` at `04db4560`.

---

## How the audit was run

| Layer        | Method                                                                                                                                                                                                        |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Size         | Every tracked source file classified line by line as code, blank or comment, by a block-comment-aware state machine; the result is regenerated by `scripts/audit-loc.mjs`, which is committed with the report |
| Structure    | Static reading of the largest modules, with a module-graph analysis over every relative import in `src/` and `frontend/src/` (edges, cycles, and which layer imports which)                                   |
| Duplication  | Repeated shapes located by reading, then confirmed by line reference — the same helper written more than once, and where the copies have already diverged                                                     |
| Churn        | `git log --numstat` over twelve months, per file, to find which large files are still moving                                                                                                                  |
| Dead code    | Every exported runtime symbol in `src/` and `frontend/src/` cross-checked against every reference in the repository, tests included                                                                           |
| Verification | Every finding re-read against the source at the cited line before it was written down; the LoC figures re-run from the committed script                                                                       |

The audit was **static**. No application was started and no browser was
driven; nothing here depends on runtime behaviour. The counting script and the
guardrail are exercised by `test/scripts/check-max-file-lines.test.ts`, which
drives them against fixture trees.

### What the code already does well

Checked and left alone. A fix in any of these would be a regression.

- **The opaque-blob invariant holds.** `sessions.command` and
  `workspaces.layout` are never parsed outside `src/services/hook-adapters/`
  and the sanctioned helpers. In the four audited route files the only
  inspections are `commandIsOpencode`, `commandModelCli`, `commandSupportsSeed`,
  `adapterHasResumeSessionArgs` and `commandAgentBin` — all named in
  `AGENTS.md`. `workspaces.layout` is not touched anywhere in them.
- **The `ScopeBackend` seam is intact.** `pty-manager.ts` reaches every scope
  operation through `getScopeBackend()` and never calls `systemd-run` or
  `systemctl` itself.
- **`github-write.ts` throws rather than swallows.** Its file header states the
  choice explicitly and contrasts it with `github-webhook.ts`. This is the
  model the rest of the backend should copy — and the reason its own swallowed
  errors are called out as a finding below.
- **`remote-host-client.ts`'s no-401-retry in `uploadProjectFile` is
  deliberate.** The body stream is single-use, so a retry would have nothing to
  resend. The comment at line 1438 says so. It looks like an inconsistency and
  is not one.
- **The REST-vs-GraphQL 404 distinction in `github-write.ts` is deliberate.**
  `githubRequest` treats a 404 as a scope error only for non-GET requests
  (line 118); `githubGraphQL` treats it as one (line 1316).
- **The rate-limit short-circuit in `githubRequest` is a documented duplicate**
  of `github-fetch.ts`'s (lines 68-70), sharing the budget without sharing the
  transport.
- **The repo already extracts.** Twenty-three `refactor(...)` commits, twelve
  of them since 2026-08-13, have already split `pty-manager` (#1543, #1553,
  #1554), `control-socket` (#1545, #1548, #2197), `session-lifecycle` (#1533),
  `App`'s hooks (#659–#666), the `sessions` approve path (#767) and the `tasks`
  review-ingest tail (#2361). `src/shared/types.ts` already absorbed ~90
  hand-mirrored API types.
- **`internal-schemas.ts` was already split out of `internal.ts`** — the
  precedent for the remaining split.
- **`project-github-writes.ts` already imports `loadProjectRepoContext` from
  `projects.js`** — the precedent for the remaining split.

## Severity model

Severity here is **blast radius × the likelihood that the next change breaks
something** — not size for its own sake. A large file that is rarely touched is
an annoyance; a large file that changed 152 times in a year is a hazard.

- **P0** — an invariant violation (the opaque-blob rule, the `ScopeBackend`
  seam, ESM specifiers, config-through-`app.config`) or a latent correctness
  bug: something that can be wrong at runtime, not merely hard to change.
- **P1** — a module whose size and churn together make the next change likely
  to break something, or a layering inversion that lets a lower layer reach
  upwards into a higher one.
- **P2** — duplicated or dead code: real maintenance cost, but it cannot
  change behaviour.
- **P3** — documentation drift and consistency nits.

**The test column is the real cost.** Every one of these modules has a test
file that is _larger than the module it covers_ — up to 3.6× for
`pty-manager.ts`. That is not bad testing; it is the direct consequence of the
monoliths: the tests are monolithic mirrors of monolithic sources, so a
refactor has to move code and tests together, and a test file that size is
itself a hazard. The ratio is also why this audit recommends extraction over
rewriting: the assertions already exist and can be moved unchanged.

**Churn overlaps size exactly.** The five largest backend files are also five
of the ten most-churned. And the three largest have never been refactored —
`projects.ts`, `task-reconciler.ts` and `internal.ts` have taken only feature
and fix commits while absorbing 6,823, 7,437 and 4,594 added lines respectively.
The repo's extraction pattern is real and working; it has simply not reached
these three.

The severity model calls a latent correctness bug P0, and one of these three

up before any of the extraction work. The other two sites lose diagnostic
text rather than misstate a fact.

## Guardrails

**`scripts/check-max-file-lines.mjs`** — no source file may grow past **1,200
code lines**.

It is a **ratchet**, not a threshold. A flat rule would fail on 59 existing
files the day it landed, so `scripts/max-file-lines.baseline.json` records
each existing offender at its current size:

- a **new** file over 1,200 lines **fails**;
- a **baselined** file over **its own** recorded ceiling **fails**;
- a baselined file **under** its ceiling passes, and the script says by how
  much the ceiling could be lowered;
- a baseline entry whose file is gone is reported, so it can be removed.

Ceilings only ever go **down**. Lowering one is the ratchet turning over: it
is a deliberate, reviewable act visible in the diff, and it is how the 59
existing offenders get fixed.

The baseline holds 59 entries — 15 production files, 43 test files and one
tooling script — because the ceiling applies to the whole source tree. Test
files are included deliberately: the audit's central finding is that the
monolithic test files are what makes the monolithic sources expensive to
change, so a ceiling that let them grow freely would leave the real problem
unaddressed.

The counting is shared with the audit that motivates the guardrail
(`scripts/lib/audit-loc-core.mjs`), so the numbers the reports quote and the
numbers the guardrail enforces are the same numbers. The script is wired into
`npm run lint` and so into `make lint`, alongside the repo's existing
`check:*` family.

## Evidence

Every number in this report is regenerated by a committed command. The
captures and raw output are regenerable and are not committed.

```bash
# the size map: per-area totals, the histogram, the largest files, the
# files over the ceiling, and the churn table
node scripts/audit-loc.mjs --top 30 --churn

# the same, as JSON
node scripts/audit-loc.mjs --json

# the guardrail on its own
node scripts/check-max-file-lines.mjs
```

The script takes the repository root as its first argument, so it can also be
pointed at any tree:

```bash
node scripts/audit-loc.mjs /path/to/tree --top 10
```
